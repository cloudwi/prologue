# 첫 방문·가입 복구·첫 연결 개선

2026-11-04 운영 배포 완료. 기능 소스는 `fbe4bf8a7a053e833ff4b2e47413eb301bcfb8ec`이며, 백엔드·웹과 호환되는 설치 앱의 운영 OTA를 반영했다. 스토어 바이너리 신규 제출과 홍보 게시·발송은 수행하지 않았다.

## 변경

- 앱·웹 가입 전 문답 체험과 소개팅 가입 5단계 구성.
- 새 앱의 신규 프로필은 `onboardingPending=true`로 저장한다. 사진과 소개팅용 프로필 문답을 저장한 다음 `PUT /members/me/onboarding/complete`로 마무리한다.
- 서버는 완료 여부를 저장하고 미완료 프로필을 소개·공개 피드에서 제외한다. 가입 완료 이벤트와 성비 게이트 등록도 마무리 시점에 처리한다.
- 앱 재진입·이메일 로그인·탭 진입 때 미완료 가입을 이어간다. 서버에 저장된 기본 정보·사진·문답을 복원하며 이미 업로드한 사진은 재전송하지 않는다.
- 소개 후보 프로필과 노출 횟수, 피드 작성자 프로필을 일괄 조회한다. 후보 순위·노출 상한·재소개 규칙은 유지한다. 후보 답변 전체 조회와 재소개 이력의 개별 조회는 후속 최적화 여지가 있다.
- 피드 이미지 요청을 DB 트랜잭션 밖으로 옮겼다. 이미지 연결·응답 제한 시간은 각 2초, 메모리 미리보기 캐시는 최대 256개다. 실패한 미리보기는 원본 사진을 공개하지 않고 생략한다.
- 공개 웹의 방문·체험 완료·다운로드·스토어 이동 이벤트를 추가했다. 운영 빌드의 `PUBLIC_POSTHOG_KEY` 설정이 있어야 활성화된다. 웹 ID와 앱 계정은 자동 연결하지 않는다.
- [첫 연결 캠페인](marketing/first-connection-campaign.md)에 게시 문구 3종, 모집 문구, 1주 운영안과 측정 기준을 준비했다. 과거 홍보 초안에는 현재 실행안 링크와 인증·소개 조건의 정정을 반영했다.

## 검증

- 백엔드 전체 테스트 576건 통과(실패·건너뜀 0). 격리된 PostgreSQL에서 V77 마이그레이션, 가입 상태 왕복, 질문별 노출 집계 쿼리를 확인했다. 이미지 서버 무응답과 본문 전송 중단도 확인했다.
- 앱 전체 테스트 185건과 TypeScript·전체 소스 ESLint 통과.
- 웹 테스트 46건과 Astro 정적 빌드 통과.
- 브라우저에서 데스크톱·390px 모바일 체험 선택, 예시 답변 1개 표시, 가로 넘침 없음, 다운로드 페이지 이동을 확인했다.
- 운영 브라우저에서 체험 선택과 다운로드 페이지 이동을 확인했다. PostHog에서 `web_landing_viewed`, `web_preview_completed`, `web_download_clicked` 수신을 확인했다. 이 세 건은 배포 검증 활동이며 실사용자 유입으로 해석하지 않는다.
- 사용자 추가 승인 후 기존 심사 계정의 운영 로그인, 프로필 조회, `PUT /members/me/onboarding/complete` 재호출과 재조회를 확인했다(모두 HTTP 200). 호출 전후 프로필 응답과 `onboardingComplete=true` 상태가 동일했다. 자격 증명·토큰·프로필 내용은 기록하지 않았다.
- 실제 iOS·Android 기기에서의 OTA 적용, 새 계정 가입·사진 업로드·미완료 계정 복구의 운영 실증, 운영 성능 변화는 아직 검증하지 않았다. 기존 완료 계정 검증은 새 가입 흐름 전체를 증명하지 않는다.

## 운영 반영 결과

1. 백엔드와 웹의 Render 배포 성공, 해당 SHA의 GitHub CI·CD 성공을 확인했다. 백엔드 공개 health·앱 설정·모임 목록 API는 HTTP 200과 정상 JSON을 반환했다.
2. 운영 Flyway V77과 `members.onboarding_complete boolean NOT NULL DEFAULT true` 적용을 확인했다. 기존 회원 6명은 모두 완료 상태이며 미완료 상태는 0명이다.
3. Render 웹 빌드 환경에 `PUBLIC_POSTHOG_KEY`를 설정한 뒤 같은 소스로 재배포했다. 공개 배포 자산의 분석 설정과 실제 이벤트 수신을 확인했다. 키 값은 이 문서와 배포 기록에 남기지 않았다.
4. 아래 운영 OTA를 발행했다. 앱 SDK와 같은 manifest 확장 헤더를 사용한 요청으로 세 조합 모두 새 업데이트 ID와 번들 GET 200을 확인했다. 단기 자산 요청 헤더는 메모리에서만 사용했다.

| --- | --- | --- |
| 1.3.1 | Android·iOS | `c81c8eb4-96c3-4255-a494-322e03903d50` |
| 1.3.2 | iOS | `8d0fb009-15a4-4bd7-bde7-579dae99fa39` |

Android 1.3.1은 기존 운영 빌드와 비교한 네이티브·설정 소스 지문 112개가 같았으며, 차이는 `eas.json`과 빌드 스크립트다. iOS 1.3.2 설치 바이너리(34)의 런타임·운영 채널을 확인했고, 이번 기능 변경에는 네이티브 의존성 변경이 없다. OTA 발행 중 임시로 변경한 앱 버전은 1.3.2로 원복했다.

상세 검증 기록은 로컬 `release/ops/deploy-20261104/`에 있다. 원복 기준은 서버·웹의 이전 소스 `6bec939885ca1b1ad7fd97dbbcfddad0c2bcf868`, 1.3.1의 이전 OTA 그룹 `200dc1ab-f8a6-49b8-a804-0c0e4787f387`, 1.3.2의 기존 내장 업데이트다. 원복은 수행하지 않았다.

운영 속도 개선 수치는 아직 측정하지 않았다. 이번 성능 검증은 쿼리 호출 구조, 트랜잭션 경계, 이미지 서버 무응답 상황의 격리된 테스트다.
