# 성장 이벤트 수집 (schema v1)

관리자: https://prologue.day/admin/growth · API: `GET /admin/growth?days=30` (ADMIN 전용, 1–90일)

## 흐름과 정합성

기존 앱의 PostHog 화면 이벤트와 별개로, 서버가 성공한 행동을 Postgres `growth_events`에 기록한다.
가입/온보딩/문답/호감/편지 저장과 이벤트 저장은 같은 트랜잭션이다. 실패하거나 롤백된 작업은 성공으로 남지 않는다.
클라이언트가 성공 이벤트를 임의로 전송하는 공개 수집 API는 없다. 기존 출시 앱·웹에서도 서버 요청만으로 작동하며 OTA/새 네이티브 빌드는 필요 없다.

- 유일키: `(account_id, event_name, SHA256(source))`. 재요청·프로세스 재시작·여러 인스턴스에서 중복 삽입을 막는다.
- `id`, `account_id`, `event_name`, `dedup_key`, 서버 `occurred_at`, `service_day`, `schema_version`만 저장한다. 임의 properties를 받지 않는다.
- 이메일/이름/성별/사진/답변/편지 내용/연락처/상대 계정 ID/요청 URL/IP를 이벤트에 넣지 않는다. 계정 UUID는 재방문 집계에 쓰는 가명 식별자이며 익명 데이터는 아니다.
- 관리자와 `review.email` 계정은 제외한다. 일반 계정으로 만든 내부 테스트 계정은 자동 구분되지 않으므로 운영 시험에 사용하지 않는다.
- 계정 삭제 시 FK CASCADE로 해당 계정 이벤트도 삭제한다. 따라서 과거 지표도 변할 수 있다.
- 원시 이벤트는 180일 보관 후 매일 KST 04:30에 삭제한다. 보고서는 최대 90일 조회한다.
- 업무 데이터와 함께 저장하므로 DB 장애 시 업무 요청도 실패한다. 성공한 요청만 기록되었다고 보장하기 위한 선택이다. 인증 활동은 기존 last-seen의 best-effort 경로다.

## 이벤트 계약

| 이벤트 | 발생 조건 | source / 중복 기준 |
|---|---|---|
| REGISTERED | 새 인증 계정 생성 | 계정당 registration 1회 |
| ONBOARDED | 첫 프로필 생성 | 계정당 onboarding 1회 |
| ANSWER_SUBMITTED | 답변 최초 저장; 수정 제외 | answer UUID |
| PEER_CHECKED | 오늘의 소개 API 정상 반환 | 이용자·서비스 날짜 |
| PEER_AVAILABLE | 위 응답에 상대가 1명 이상 있음 | 이용자·서비스 날짜; 실제 화면 노출과 구분 |
| HEART_SENT | 최초 호감 저장 | heart UUID |
| MAIL_SENT | 편지 발송 저장 | mail UUID |
| MAIL_REPLIED | 서로 편지 발송 후 늦게 보낸 쪽 | 정렬한 두 mail UUID |
| MAIL_REPLY_RECEIVED | 위 연결에서 먼저 보낸 쪽 | 위와 동일 |
| CONTACTS_EXCHANGED | 상호 발송한 두 이용자 각각 | 위와 동일; 쌍 집계는 distinct dedup_key |
| ACTIVE_DAY | 유효 토큰으로 인증 요청 | 이용자·서비스 날짜 |

답장/연락처 교환은 커밋된 `mails`를 내구성 있는 원천으로 삼는 projection이 60초마다 생성한다.
동시 발송, 중단 후 재시작도 재조회로 회복한다. 회당 200쌍을 처리하므로 backlog가 크면 지연될 수 있다.
한 쌍의 네 이벤트는 동일 트랜잭션으로 기록하며, 원래 두 번째 발송 시각을 이벤트 시각으로 쓴다.
수집 시작 이후 새로 이루어진 상호 발송만 집계한다. 기존 첫 편지에 수집 시작 후 답장이 온 경우는 포함한다.
이는 두 사람이 연락처를 **제공**했다는 사실이다. 둘 다 읽었거나 실제 만났음을 의미하지 않는다.

## 전환과 재방문 정의

서비스 날짜는 기존 `ServiceDay`의 KST 오전 5시 경계를 사용한다. 보고서 기간은 해당 날짜 단위로 시작하고 현재 시각까지다.
`growth_collection.started_at`이 최초 측정 시점이다. 과거 이벤트를 소급/추정하지 않는다.

- 가입→문답, 소개→호감/편지, 발신→답장 수신: 조회 기간의 사용자별 첫 진입 행동 이후 **7×24시간 미만**에 성공 행동이 있었는지 계산한다. 관찰 7일이 끝난 코호트만 분모에 넣는다. 사용자 단위이며 같은 상대/편지에 대한 전환을 보장하는 지표는 아니다.
- 답변→소개: 종료된 서비스 날짜별 신규 답변 작성자 중 같은 날짜에 `PEER_AVAILABLE`이 있는 비율. 나중 도착한 소개도 반영하며, 이미 도착해 있던 카드를 확인한 경우도 포함한다.
- D7: 가입 서비스 날짜 +7일에 `ACTIVE_DAY`가 있는지. +8일이 시작된 코호트만 분모에 넣는다. D7 이후 아무 날이나 돌아오는 rolling retention과 다르다.
- 분모가 0이면 percent=null, UI는 ‘집계 대기’. 신규 수집 첫 주에 0% 이탈로 오인하지 않는다.
- `events`는 행동 수, `users`는 distinct 계정 수다. ACTIVE_DAY의 events는 이용자·날짜 수다.
- 활성은 인증된 요청의 근사 지표로 백그라운드 요청이 포함될 수 있다. 앱 foreground 방문·웹 익명 유입·광고 출처/캠페인·실제 만남·이탈 이유는 이 파이프라인에 포함하지 않는다. 기존 PostHog 행동 이벤트와 서버 사실을 더해서 합산하면 안 된다.

## 운영 확인

- `/admin/growth`에서 시작 시점, 기간별 행동 수/이용자 수, 관찰 완료 코호트를 확인한다.
- 배포 직후 0과 집계 대기는 정상이다. 기존 회원 행동 수는 즉시 쌓이지만 신규 가입 코호트 전환율에는 시간이 필요하다.
- projection 오류는 서버 스케줄러 로그/기존 오류 모니터링에서 확인한다. 성공했는데 성장 이벤트가 빠지는 경우를 정상으로 간주하지 않는다.
- 예시 SQL: `select event_name, count(*) from growth_events group by event_name;` (접근은 운영 권한으로 제한)
- 검증: 실제 PostgreSQL Flyway/쿼리, 중복·롤백·삭제·관리자/심사 제외, 코호트 성숙/순서/7일 경계, 상호 발송 projection 재실행, 비관리자 차단 테스트.
